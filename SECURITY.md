# Безопасность Pulse

Отчёт о проверке и правила, которые держат кабинеты пользователей раздельными.
Проверка: 16.10.2026, по чек-листу OWASP Top 10 (A01 доступ, A02 криптография/секреты,
A03 инъекции/XSS, A05 настройки, A07 аутентификация, A08 целостность кода).

## Как устроено

| Часть | Где работает | Что знает |
|---|---|---|
| Сайт (`index.html`, `app.js`) | GitHub Pages, у пользователя в браузере | Только публичный адрес Supabase и publishable (anon) ключ |
| Вход и регистрация | Supabase Auth | Почта и хеш пароля (пароли сайт не хранит) |
| Данные | Supabase Postgres, таблица `public.items` | Строки с владельцем `user_id` |

Главное правило: **доступ проверяет база, а не сайт.** Даже если кто-то перепишет код
страницы у себя в браузере или будет слать запросы напрямую, база отдаст ему только
строки, где `user_id` совпадает с id из его собственного токена входа.

## Что сделано

**Изоляция кабинетов (A01)**
- Row Level Security включена и принудительна (`force row level security`) для `public.items`.
- Четыре политики (select / insert / update / delete) — только `user_id = auth.uid()`.
- Роль `anon` (не вошедший) не имеет к таблице никаких прав.
- Триггер всегда ставит `user_id` из токена — подделать владельца или «передать» запись чужому аккаунту нельзя.
- Удаление аккаунта удаляет все его данные (`on delete cascade`).

**Ключи и секреты (A02)**
- В репозитории нет секретов. `config.js` содержит только публичный адрес и publishable/anon ключ — они видны всем по замыслу Supabase.
- `service_role` / `secret` ключ нигде не используется. Проверка в GitHub Actions падает, если он появится в публичных файлах.
- gitleaks проверяет всю историю коммитов на утёкшие ключи.

**Инъекции и XSS (A03)**
- Весь пользовательский текст выводится через экранирование (`esc`).
- В разметке нет `onclick=` и встроенных скриптов: действия идут через диспетчер с белым списком.
- Content-Security-Policy: `script-src 'self'` — браузер не выполнит никакой код, кроме файлов сайта;
  `connect-src` — только Supabase; `form-action 'none'`, `base-uri 'none'`, `default-src 'none'`.
- Запросы к базе идут через REST с параметрами, без сборки SQL; `id` и раздел проверяются по белому списку и регулярному выражению и в браузере, и в базе.

**Ограничения в базе (A04/A05)**
- Только 8 разрешённых разделов, `id` по шаблону, `data` — только JSON-объект до 32 КБ, не больше 20 000 записей на аккаунт.

**Аутентификация (A07)**
- Пароль минимум 8 символов, вход и восстановление — через Supabase Auth.
- Сообщение «восстановить пароль» не раскрывает, есть ли такой аккаунт.
- Выход стирает токен и все данные со страницы; токен обновляется автоматически.
- Защита от встраивания сайта в чужую страницу (frame-busting).

**Целостность кода (A08)**
- Нет сторонних JS-библиотек и CDN-скриптов: весь код — в этом репозитории.

## Автоматические проверки (GitHub Actions → «Проверка безопасности»)

1. **RLS-тест на настоящем PostgreSQL** (`tests/run_rls_test.sh`): два пользователя, 17 атак —
   чтение, изменение, удаление чужих записей, подделка владельца, upsert поверх чужого ключа,
   доступ гостя и с битым токеном, слишком большие и некорректные данные. Последний прогон: **17/17 OK** (+15 проверок изоляции подписок на уведомления, +22 проверки автозагрузки здоровья).
   Контрольный прогон с выключенной RLS ловит 5 дыр — значит, тест действительно проверяет защиту.
2. **Поиск секретов** (gitleaks + проверка, что в `config.js` ключ только с ролью `anon`).
3. **Разбор выписок** (`tests/statements/check_tables.cjs` в CI, `check_pdf.cjs` локально): образцы PDF, CSV и Excel в форматах Сбера, Т-Банка, Альфа-Банка, ВТБ и таблиц «Приход/Расход» — число операций и суммы совпадают до копейки.
4. **Сквозной тест в браузере** (`tests/e2e.cjs`, запускается локально с мок-сервером Supabase): 107/107 OK —
   регистрация двух людей, изоляция данных, XSS, выход, неверный пароль, привычки, финансы и обязательные платежи, загрузка выписки (без дублей, XSS из файла показывается как текст, битый файл не ломает страницу), группы и стикеры заметок, отсутствие нарушений CSP.

**Загрузка банковских выписок**
- Файл выписки читается только в браузере (`bank.js`, `vendor/pdfjs/`) и никуда не отправляется. В базу уходят лишь найденные операции: дата, сумма, описание, категория.
- PDF читает pdf.js 3.2.146 (Mozilla), лежит в репозитории, без CDN. Известная уязвимость старых версий (CVE-2024-4367) закрыта дважды: `isEvalSupported:false` и CSP без `unsafe-eval`; к тому же страницы не рисуются, берётся только текст.
- CSP дополнена `worker-src 'self'` (pdf.js работает в фоновом потоке) и `connect-src 'self'` (таблицы шрифтов pdf.js с этого же сайта).
- Ограничение файла — 25 МБ. Описание операций из файла всегда экранируется.

**Пуш-уведомления**
- Подписка телефона хранится в `push_subs` (RLS: каждый видит и удаляет только свои). Добавить подписку можно только функцией `push_subscribe`, она всегда ставит владельцем того, кто вошёл, и принимает только адреса настоящих push-сервисов (Apple, Google, Mozilla, Microsoft) — сервер не отправит запрос на чужой адрес.
- Ключи VAPID и секрет расписания лежат в закрытой схеме `private` (RLS, без политик, без доступа из приложения); их читает только серверная функция через `push_admin_config` (только service_role). Ключи создаются сами внутри Supabase и никогда не покидают его.
- Расписание (pg_cron) раз в минуту вызывает функцию `push` с секретом; без секрета функция отвечает 403. Проверочное уведомление требует вход и ограничено одним раз в 20 секунд.
- Текст уведомления шифруется для конкретного телефона (RFC 8291): Apple/Google видят только зашифрованные байты. Шифрование сверено с официальным примером из стандарта независимой библиотекой.
- Замечания Supabase Advisor: «RLS без политик» у `private.push_config` и `push_sent` — так задумано (таблицы закрыты полностью); `push_subscribe` доступна вошедшим — так задумано (см. выше); `pg_net` в схеме public — служебное расширение Supabase, данных в нём нет.

## Обязательные настройки в панели Supabase

1. **Authentication → Sign In / Providers → Email**: «Confirm email» включено.
2. **Authentication → URL Configuration**: Site URL и Redirect URLs = `https://danuhappy.github.io/Pult/`
   (только этот адрес — иначе ссылки из писем можно увести на чужой сайт).
3. **Authentication → Policies / Passwords**: минимальная длина пароля 8+.
4. **Advisors → Security Advisor**: не должно быть предупреждений по `public.items`.
5. Секретный ключ (`service_role` / `sb_secret_…`) никому не отправлять и никуда не вставлять.

## Остаточные риски (известны и приняты)

- Токен входа хранится в `localStorage` браузера (стандарт для таких сайтов). Риск — XSS; он закрыт экранированием и строгой CSP.
- GitHub Pages не позволяет ставить HTTP-заголовки, поэтому защита от встраивания сделана скриптом, а не заголовком `frame-ancestors`.
- Шрифты грузятся с Google Fonts (Google видит IP посетителя). Можно перенести шрифты в репозиторий.
- Безопасность почты и пароля пользователя — на его стороне; двухфакторный вход можно включить позже (Supabase MFA).

## Автозагрузка из Apple Здоровье
Команда в «Командах» iPhone отправляет шаги, сон и вес на `rpc/health_ingest` с личным ключом (`supabase/health.sql`).
В базе хранится только SHA-256 хэш ключа (закрытая схема `private`). Ключ умеет лишь дописать эти три значения в свой день здоровья
за последнюю неделю — читать или удалять данные им нельзя; не больше 60 загрузок в час; «Новый ключ» или «Отключить» сразу отзывает старый.
Значения проверяются на реальность (шаги до 200 000, сон до 24 ч, вес 20–400 кг).
